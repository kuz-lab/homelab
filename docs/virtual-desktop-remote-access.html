Remote Virtual Desktop

Connecting a Meta Quest 3 to Virtual Desktop Streamer on a MacBook from outside the home network, through port forwarding on OPNsense — the setup, the verification procedure, and the three silent failures that made it look like a carrier problem.

01 How remote mode actually works

Worth understanding before touching the firewall, because it dictates which NAT settings are load-bearing.

  1. The Streamer holds a permanent outbound TCP connection to the Virtual Desktop cloud (Azure — 40.89.161.236 was observed), using source port 38810.
  2. The headset signs in to the same cloud and sees the computer in its list. This works even when no direct path exists, so "the computer is visible" proves nothing about the network.
  3. On a connection attempt the cloud tells each side the other's address and TCP hole punching begins: the Mac dials the headset, the headset dials the Mac, and the Streamer opens a LISTEN socket on 38810 at the same moment.
  4. A headset on mobile data sits behind symmetric carrier-grade NAT almost every time, so the Mac's outbound punch never lands. The only path that survives is the headset's inbound connection to your forwarded port.
The consequence that matters

The public port the cloud advertises to the headset must be the same port you forwarded. By default pf randomizes the source port during translation, so the cloud advertises a random high port with nothing behind it. That makes static port mandatory, not optional — see section 03.

Don't over-forward

Official documentation lists only the four TCP ports. UDP 38850 was added here after observing it on the macOS build, but it was never proven necessary. In a fresh setup, forward TCP only until you hit a problem that UDP demonstrably solves.

02 The Mac side

  • Streamer installed and signed in to the same account as the headset.
  • Allow remote connections, Start with macOS and Ask for computer access all enabled. The first remote connection raises a confirmation dialog on the Mac — accept it, or the connection drops.
  • macOS Application Firewall either off, or with the Streamer explicitly allowed.
  • A fixed IP address. This is a requirement, not a nicety: the forward points at one specific address. Set it as a DHCP static mapping in OPNsense.
  • If Private Wi-Fi Address is on for this network, switch it to Fixed. On Rotating, the MAC changes and the DHCP reservation stops matching.
ipconfig getifaddr en0

03 OPNsense configuration

Subsections are in execution order.

3.1 · Host alias

Firewall → Aliases → create a Host(s) alias named HOST_MAC containing exactly one address, 192.168.10.10.

Failure ②

With more than one address in the alias, pf loads the forward with a round-robin flag and distributes connections across the addresses in turn. Half the attempts land on a host where nothing is listening and die silently — no log entry, no rejection.

pfctl -t HOST_MAC -T show

Expect exactly one line.

3.2 · Source NAT — static port

Firewall → NAT → Source NAT (called Outbound in older releases). Set the mode to Hybrid outbound NAT so the automatic rules survive, then add one rule per port or a single rule for the range.

Press Apply once all rules are saved.

Failure ③ · the Firewall rule field
  • Manual — no pass rule is created at all. The forward exists, but the translated packet is destroyed by the default-deny policy. This is the default value and the nastiest failure of the three: in the GUI everything looks configured.
  • Pass — works via rdr-pass, bypassing the filter set. The rule never appears under Firewall → Rules, isn't logged, and ignores rule ordering.
  • Register rule — creates a linked rule that is visible and editable under Firewall → Rules → WAN, with logging. The right choice.
pfctl -sr | grep 388

Expect one line per port:

pass in quick on pppoe0 reply-to (pppoe0 <GW>) inet proto tcp \
     from any to <HOST_MAC> port = 38810 flags S/SA keep state

The reply-to clause is essential on PPPoE — it guarantees the reply leaves through the same interface. If no lines appear after Apply, stop here; nothing downstream will work.

04 Verification

Test the transport separately from the application. That is what tells a network fault apart from a Virtual Desktop fault.

Three ways to test nothing at all

Invalid tests
  • Testing from inside the network. Reaching <WAN_IP> from any home device, including the Mac itself, is a hairpin request that cannot work without NAT reflection — by design.
  • Phone silently back on home Wi-Fi. Turn Wi-Fi off in Settings, not in Control Center — from there it re-enables itself and rejoins the home network. Confirm by opening https://ifconfig.me on the phone; it must show a carrier address.
  • Streamer and test server running together. They compete for port 38810 and only one wins.

Transport test

On the Mac, from an empty directory — the server publishes the current directory to the internet:

mkdir -p /tmp/vdtest && cd /tmp/vdtest && python3 -m http.server 38810 --bind 0.0.0.0

From the phone on mobile data, open http://<WAN_IP>:38810.

Success looks like this 
<CARRIER_IP> - - [16/Aug/2026 05:09:45] "GET / HTTP/1.1" 200 -

That single line proves the whole chain: internet → pppoe0 → DNAT → pass rule → vlan02 → Mac. Stop the server and remove the directory afterwards.

Live test

  1. Start Virtual Desktop Streamer.
  2. Confirm it owns the ports: lsof -nP -iTCP | grep 388 — expect the cloud connection plus bindings on 38820/38830/38840.
  3. Put the headset on an outside network and connect.

05 Diagnostics

Bisecting the break

Walk the chain in order. Each step splits the problem space in half and rules out an entire class of causes.

  1. Is the Streamer listening? lsof on the Mac. If not, the fault is in the application and the network is irrelevant.
  2. Does the Mac's address match the alias? ipconfig getifaddr en0 against pfctl -t HOST_MAC -T show.
  3. Has the public address changed? A PPPoE session reconnects and the address can move — the argument for dynamic DNS.
  4. Does the packet reach the WAN? Capture on pppoe0 during an attempt. If not, the fault is in the outside network or the carrier.
  5. Does it reach the inside interface? Capture on vlan02. Present on WAN but absent here means a filter is dropping it, or the alias is wrong.
  6. Does the Mac reply? Capture on the Mac. SYN in with no SYN-ACK out means something on the host is blocking.

07 What was actually broken

Three independent defects, each sufficient on its own to break the connection completely. The combination is what made diagnosis hard: fixing any one of them changed nothing observable, which kept pointing suspicion at the carrier.

①

Source port randomization in Source NAT

The Streamer talked to the cloud from port 38810, but it left the router as 46677, so the cloud advertised 46677 to the headset — a port with nothing behind it.

→ enable Static port
②

The alias held two addresses

192.168.10.10 and 192.168.10.11. The rdr rule loaded with round-robin and sent a share of connections to a host that did not exist.

→ one address in the alias
③

No pass rules existed at all

The Firewall rule field on every Destination NAT entry was set to Manual. The forwards looked configured in the GUI, but translated packets were destroyed by the default-deny policy.

→ Register rule + Interface = WAN
The wrong theory, and how it died

"The carrier's double NAT is to blame" was the leading hypothesis for hours. It was plausible and it matches plenty of community reports — symmetric CGNAT really does block hole punching from the Mac's side. It was killed by one packet capture: tcpdump on pppoe0 showed SYNs arriving from the carrier address before any fix was applied. The traffic was reaching the WAN the whole time. The problem was always inside the perimeter.

The lesson: before accepting any theory that blames something outside your control, capture on the WAN interface. It answers "whose fault is this" in about a minute.

08 Security and alternatives

What this setup costs

Four TCP ports of a proprietary service are exposed to the entire internet. Mitigations in place: the rules target a single destination host, they were created through Register rule so they are visible and logged, and the Mac sits in a Trusted VLAN behind an inter-VLAN default-deny policy. The residual risk is real — any flaw in the Streamer's network code is reachable from the internet with no perimeter authentication in front of it.

The better path for travel

For connecting from arbitrary Wi-Fi networks and other countries, Tailscale installed on the Quest via the official Android APK (developer mode required on the headset) is both safer and more reliable:

  • zero open ports on the WAN;
  • WireGuard authentication plus your tailnet identity, instead of trusting a proprietary service;
  • independent of the NAT type on the far side — when no direct path exists it falls back to a DERP relay, which is unusable for VR latency but fine for desktop work;
  • captive portals are only partly solved — hotels may still need a travel router running Tailscale.

The sensible end state: keep the direct forward as a fast path for networks without symmetric NAT, and make the VPN the default when travelling.

Maintenance

  • A DHCP static mapping for the Mac is mandatory, not optional.
  • Dynamic DNS on OPNsense if the public address is dynamic.
  • Re-check the port set after Streamer updates — the macOS build was rewritten in the 1.34 branch and its observed behaviour already differs from the documentation.

09 Checklist

  • Mac has a fixed address; Private Wi-Fi Address set to Fixed
  • Streamer: Allow remote connections, Start with macOS, Ask for computer access
  • Alias holds exactly one address
  • Source NAT with Static port covers ports 38810–38850
  • Four Destination NAT rules: Interface = WAN, Firewall rule = Register rule
  • Four pass rules loaded — pfctl -sr | grep 388
  • Transport test from mobile data returns GET /
  • Test server stopped, Streamer restarted
  • Headset connects from an outside network
